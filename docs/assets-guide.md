# Public asset guide

Everything inside `public/` is served without authentication. An unlinked file is
still public after deployment. Store only approved publication-safe material.

## Directory structure

```text
public/
├── images/
│   ├── profile/     approved profile photographs
│   ├── projects/    sanitized covers and case-study galleries
│   └── social/      optional static social previews
├── documents/       approved downloadable PDFs
├── icons/           optional public component icons
└── README.md        public-directory boundary reminder
```

The active favicon is `src/app/icon.svg`, and the default social preview is
generated by `src/app/opengraph-image.tsx`. Those use Next.js App Router metadata
conventions rather than `public/`.

## Supported and preferred formats

The content validator accepts:

- `.avif` — preferred when the export workflow produces reliable quality;
- `.webp` — preferred general-purpose web image;
- `.jpg` / `.jpeg` — suitable for photographs;
- `.png` — suitable for diagrams or UI captures requiring lossless detail.

Use SVG for trusted, hand-reviewed icons/logos only. The current typed project
image model deliberately does not accept SVG because screenshots and photographs
do not need active vector content.

PDF is the supported downloadable document format.

## Recommended dimensions

| Asset | Recommended source size | Composition |
|---|---:|---|
| Profile portrait | 1600 × 2000 | 4:5, subject safe at mobile crop |
| Project cover | 1600 × 1000 | 16:10 |
| Project gallery | 1600px wide or larger | Consistent within one case study |
| Social preview | 1200 × 630 | 1.91:1 |
| Favicon source | Square SVG/viewBox | Simple at 16–64px |

These are preparation recommendations, not rendered CSS dimensions. Always enter
the file’s real intrinsic `width` and `height` in content.

Avoid upscaling a small source. Test legibility of UI screenshots at the actual
rendered mobile size.

## File naming

Use lowercase kebab-case:

```text
umar-portrait.webp
snakinesis-control-loop.webp
ets-website-sanitized-content-flow.png
muhammad-umar-nadeem-resume.pdf
```

For project media, begin with the project slug and describe the subject. Do not
put employer-internal IDs, person names, dates of private events, environment
names, or “final-final-v2” in filenames.

## Optimization

Before committing:

1. Crop unused canvas.
2. Remove EXIF/GPS and unnecessary document metadata.
3. Export photographs as AVIF/WebP/JPEG at visually sufficient quality.
4. Use PNG only when lossy compression harms diagrams or text.
5. Confirm text in screenshots remains readable.
6. Avoid embedding full-resolution originals when a smaller public derivative is
   sufficient.
7. Check the Git diff and file size.

As a practical target, keep ordinary covers well below 500 KB and full gallery
images below 1 MB when quality allows. These are review thresholds, not reasons
to make text illegible.

`next/image` handles responsive delivery for typed profile and project images,
but it cannot remove confidential pixels or metadata from the source file.

## Replace the profile photo

1. Obtain explicit approval for public use.
2. Prepare a 4:5 image with safe mobile and desktop crops.
3. Remove location metadata.
4. Place the file in `public/images/profile/`.
5. Set `profile.portrait` in `src/content/profile.ts` with path, descriptive alt,
   intrinsic width/height, and optional caption.
6. Run `npm run validate:content`.
7. Inspect both themes at 390px, 768px, and desktop width.
8. Remove the replaced file once no content references it.

`portrait: undefined` intentionally renders the current designed placeholder.

## Add a project cover

Place the approved image in `public/images/projects/` and set:

```ts
coverImage: {
  src: "/images/projects/project-slug-cover.webp",
  alt: "Description of the meaningful visible state",
  width: 1600,
  height: 1000,
  caption: "Optional visible context.",
},
```

The cover renders inside the homepage project card. Check that it does not
overwhelm the evidence hierarchy or expose private data.

## Add gallery images

Set an ordered `gallery` array on the project. Gallery images render in a
two-column desktop grid and a one-column mobile stack.

Use the array order to tell a coherent sequence. A gallery is not a dumping
ground; each image should prove a distinct decision or outcome.

For ETS or Sentinel, approval and sanitization are required before a file enters
`public/`, even temporarily.

## Social preview images

The default `/opengraph-image` is generated from public profile/site settings in
`src/app/opengraph-image.tsx`.

To use a static social image in the future:

1. Export 1200 × 630 to `public/images/social/`.
2. Add the path through Next.js Metadata in `src/app/layout.tsx` or the relevant
   project metadata.
3. Add a documented typed setting if maintainers need to replace it routinely.
4. Verify the absolute URL using the production `NEXT_PUBLIC_SITE_URL`.

Do not maintain an unused static duplicate of the generated image.

## Favicons and icons

- Active favicon: edit `src/app/icon.svg`.
- Public component icon: place a reviewed file in `public/icons/` and reference
  it root-relatively.
- Prefer simple code-native SVG for brand marks.
- Do not use remote icon URLs or an icon package for one asset.

Check contrast against both light and dark browser chrome where applicable.

## Technology logos

Project stack badges resolve through `src/content/technology-icons.ts` to local
files under `public/icons/technologies/`.

Rules:

1. Use official brand assets or reputable canonical sources (for example Simple
   Icons CC0 marks, or vendor documentation SVGs).
2. Store files locally. Do not hotlink. Do not use AI-generated logos.
3. Keep readable text labels beside logos in `TechnologyBadge`.
4. Provide `iconDark` only for monochrome marks that need a white/light variant.
5. Do not invert multicolor logos with CSS filters.
6. Set `logoSafeSurface: true` only when a mark needs a small neutral pad on
   maroon/charcoal project cards.
7. Do not recolor every logo to the brand maroon.
8. Cloudflare Turnstile uses the Cloudflare mark with the explicit label
   `Turnstile` (`turnstile.svg`). Classify Turnstile under `integrations`, never
   under `deployment`.
9. Streamlit Community Cloud reuses the Streamlit mark with the explicit label
   `Streamlit Community Cloud`.

## Résumé files

1. Export an approved PDF.
2. Review every claim against the source of truth.
3. Remove hidden comments, tracked changes, authoring metadata, and unnecessary
   personal information.
4. Place it in `public/documents/`.
5. Set `profile.resumePath`.
6. Validate and test the footer download.
7. Delete replaced public versions.

Never store source résumé documents containing private notes in `public/`.

## Alt text

Alt text is required for every typed image.

Good:

> Sanitized workflow diagram showing a request moving through review and approval.

Weak:

> Screenshot.

Avoid:

- “image of” or “picture of”;
- filenames;
- claims not visible in the image;
- duplicate adjacent captions;
- confidential names or records.

Decorative visuals should normally remain CSS or use an empty alt only when the
component intentionally supports decorative media. The current portfolio image
model expects meaningful content and therefore rejects empty alt text.

## Import versus `public/`

Use `public/` when:

- a typed content entry references the asset;
- a stable public URL/download is required;
- a maintainer should replace the file without changing component imports.

Use a code import or App Router convention when:

- the asset is implementation-specific;
- it belongs to metadata conventions (`src/app/icon.svg`);
- compile-time coupling is desirable;
- it is a small code-native visual, not editable portfolio content.

Do not fetch portfolio assets from arbitrary remote storage.

## Remove unused assets

Before deletion, search:

```bash
rg -n "filename\\.webp|filename\\.pdf" src docs public
```

Then remove only the exact unreferenced file. Run `npm run validate:content` and
`npm run build`.

The validator catches referenced files that are missing. It does not currently
delete or flag every unreferenced public file because historical/download
intent cannot be inferred safely; maintainers must review unused files
deliberately.
